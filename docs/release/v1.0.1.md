# source-lang v1.0.1 — end of input in the last source, cached lines, bounded reads

**Patch release.** No public API changes and **no layout changes**: every source's
base and every interior `locate` answer is identical to 1.0.0. Three fixes from the
toolchain issue ledger: the end of the last source resolves to it (H04, the
non-breaking part), `line_col` no longer rescans the source on every call (M20), and
`add_file` can no longer read without bound (M21).

## What is source-lang?

The multi-file coordinate layer of a compiler front-end. It loads files and
in-memory buffers, gives each a stable `SourceId`, lays them out in one global
position space, and maps any global position back to the source and local offset —
or the file, line, and column — it came from.

## Fixed

### The end of the last source resolves to it (H04)

Every "found end of input" diagnostic points at a zero-width span at the end of the
text, `Span::empty(len)`. Up to 1.0.0 that position returned `None` for the last
source, so diag-lang rendered the error as "outside the loaded sources" with no
frame; lang-forge, which parses one source per map, hit this on every
end-of-input error.

`locate` (and `line_col`) now resolve the end of the **last** source (the end of
the global space) to that source, at a local offset equal to its length
(`line_col`: one column past the last character). An empty last source is
locatable too. Everything else is unchanged: membership stays half-open.

```rust
use source_lang::{BytePos, LineCol, SourceMap};

let mut map = SourceMap::new();
let a = map.add("a", "abc").expect("fits"); // 0..3
let b = map.add("b", "de").expect("fits");  // 3..5

assert_eq!(map.locate(BytePos::new(2)), Some((a, BytePos::new(2))));
assert_eq!(map.locate(BytePos::new(3)), Some((b, BytePos::new(0)))); // unchanged
assert_eq!(map.line_col(BytePos::new(5)), Some((b, LineCol::new(1, 3)))); // new
assert_eq!(map.locate(BytePos::new(6)), None);
```

### `add_file` reads are bounded (M21)

The metadata pre-check stays, and the read itself now goes through
`take(max_source_len + 1)`. A pipe, a `/proc` file (metadata length 0), or a file
growing while it is read stops one byte past the ceiling and fails with
`SourceMapError::Oversize`, whose `len` is then the bytes read (`max + 1`), a lower
bound. The buffer is pre-sized from the metadata length.

## Changed

### `line_col` uses a line table built once (M20)

Each source's line starts are computed once, when it is added (one pass, exact-size
allocation, 4 bytes per line), and kept in a side table indexed by `SourceId`;
`SourceFile` itself is unchanged. `SourceMap::line_col` is now
`O(log files + log lines)` plus a character count within the located line; it used
to build a full `LineIndex` over the source on every call. `locate` searches a dense
array of start offsets instead of the `SourceFile` records. `SourceFile::line_index`
still builds a fresh index per call, because `span-lang` 0.4's `LineIndex` has no
constructor that could adopt the cached table.

## Known limitation (fixed in 2.0)

Sources are laid out contiguously, so the end of a source that is **not** the last
one is the same position as the next source's first byte. That position resolves to
the next source at `1:1`, as in 1.0.0, so an end-of-input diagnostic for an earlier
source is attributed to the following source. An empty source that is not the last
one stays unlocatable for the same reason. The fix reserves one end position per
source (rustc's layout). It shifts every later base, which breaks code that
predicts bases from lengths (repl-lang does), so it is semver-major and planned for
source-lang 2.0.

## Consumer check

The full test suites of repl-lang, module-lang, and lexer-lang (which depend on
source-lang) and lang-forge (which depends on diag-lang) pass unchanged against
this release (patched in locally with `cargo update -p … --config patch…`).

## Benchmarks

Criterion, Windows x86_64, Rust 1.95, release profile. "Before" is the `v1.0.0`
tag's code built from a clean export with the identical bench file; old and new
were run back to back. The machine was shared with another build session, so expect
some noise on the sub-10 µs figures.

| Benchmark | v1.0.0 | v1.0.1 |
|---|---|---|
| `line_col_1m/16x1000_lines` (1,000,000 lookups, 16 files x 1,000 lines) | 14.164 s | 28.783 ms |
| `line_col/16` (1,024 lookups, 256-byte files) | 178.74 µs | 23.036 µs |
| `line_col/256` | 389.33 µs | 31.909 µs |
| `line_col/4096` | 222.17 µs | 45.856 µs |
| `line_col/65536` | 286.06 µs | 75.280 µs |
| `locate/16` (1,024 lookups), runs 1 / 2 / 3 | 3.8400 / 4.6892 / 4.9375 µs | 4.4651 / 4.3979 / 4.4239 µs |
| `locate/256` | 7.9340 / 9.9662 / 10.279 µs | 7.9299 / 8.4366 / 8.3180 µs |
| `locate/4096` | 15.767 / 20.650 / 21.243 µs | 12.578 / 14.387 / 14.170 µs |
| `locate/65536` | 38.194 / 55.613 / 55.294 µs | 36.070 / 37.379 / 41.528 µs |

`locate/16` was 16% slower in run 1 and 6–10% faster in the two interleaved reruns.
All other sizes are at parity or faster in every run.

## Breaking changes

**None.** The API is unchanged and the layout is unchanged. The one observable
change: the end of the last source, which returned `None`, now resolves to it.
